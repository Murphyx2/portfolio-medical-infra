01

Architecture

Clean bill of health. The codebase is already unusually well-consolidated — several shared modules (SwapPermissionsMixin, apply_masking, CoreModelSerializer, the frontend ListPage shell) carry docstrings documenting the exact duplication they were built to eliminate. What remains is residue that escaped those refactors, not an unaddressed pattern. Verified clean: cross-app model imports, PII-masking duplication, reference-data CRUD boilerplate, RBAC gating, and the shared fetch wrapper.

Low

Three ViewSets hand-roll logic that SwapPermissionsMixin already exists to replace

SwapPermissionsMixin in apps/core/mixins.py exists specifically to eliminate a repeated get_permissions() body — but two doctors ViewSets and one centers ViewSet still write it by hand instead of inheriting the mixin.

backend/apps/doctors/views.py:46-53 backend/apps/doctors/views.py:97-105 backend/apps/centers/views.py:45-48
RecommendationAdd SwapPermissionsMixin to each class's bases and replace the hand-written method with a write_permission_classes assignment, matching AppointmentViewSet/EncounterViewSet.
Info

Reportes app keeps a private copy of the swap-permissions idiom

_ReportesSwapPermissionsMixin reimplements the same shape as the shared mixin, keyed on viewer/editor roles rather than SAFE/non-SAFE — a legitimately different policy, not pure duplication, but a second private copy of the idiom living outside apps/core.

backend/apps/reportes/views.py:25-35
RecommendationNo urgent merge — the shared mixin would need an action-based branch it doesn't have today. Flagged for awareness only.
Info

A 2-line role check is repeated twice in the same file

const isCenterManager = user?.role === "CENTER_MANAGER" appears in two different components inside the same file — a business-logic branch, not an RBAC bypass, but worth hoisting to avoid drift.

frontend/src/pages/Reportes.tsx:196-197 frontend/src/pages/Reportes.tsx:437-438
RecommendationExtract a small useIsCenterManager() hook or a top-of-file constant.
9 areas checked and found clean
  • Cross-app model imports — every apps/*/models.py import is apps.core.* (allowed shared infra); no app imports another app's model directly.
  • PII masking — apps/core/masking.py::apply_masking is the single funnel; every masking-eligible serializer routes through it declaratively.
  • CoreModelSerializer is used consistently everywhere an active field / masking need exists; the serializers that skip it correctly have no such need.
  • Reference-data CRUD — ReferenceDataViewSet is reused by all 9 reference-list endpoints, not reimplemented per app.
  • Center-scoping helper (user_accessible_center_ids) has exactly one implementation.
  • Frontend list/table shell — ListPage.tsx is shared by 15 page files; its own docstring notes it replaced byte-identical copy-paste.
  • Modal/dialog primitives (Dialog, FormModal, ConfirmDialog) are shared; page-specific dialogs build on top rather than reimplementing chrome.
  • RBAC gating — can.ts is the only role-check surface outside legitimate business-logic branches.
  • Fetch wrapper — only services/api.ts calls fetch directly anywhere in the frontend.
02

Security

Two high-severity findings, both confirmed by direct inspection. Everything else checked — JWT handling, PII encryption, media token auth, response headers, dependency versions, the WhatsApp webhook signature check — came back clean.

High

Live production secrets sitting in an untracked, non-gitignored file

A stray file with a leading-space filename holds the currently active DJANGO_SECRET_KEY, PII_FIELD_KEY, POSTGRES_PASSWORD, and REDIS_PASSWORD, byte-identical to the real .env. Because the filename doesn't match .gitignore's .env / .env.* patterns, git status shows it as untracked-but-not-ignored — a broad git add would commit real secrets.

infra/ - Copy.env
Corrected during verification: the audit agent also reported a second copy at backend/ - Copy.env — checked directly, that file does not exist. Only the infra/ copy is real.
RecommendationDelete the file (not committed anywhere — git log --all -- "*.env" returns empty, so no history exposure). Consider broadening .gitignore to catch stray env-like filenames going forward.
High

Patient name shown unmasked to IT and Center Manager in Comunicaciones

DeliverySerializer.get_patient_name returns the patient's real full_name with no is_masked_role/apply_masking gate — unlike every other PII-bearing serializer in the app. The endpoint is reachable by all six roles including IT and Center Manager, whose PII should be masked per the project's own masking policy. This is a regression introduced in the newer Comunicaciones module, not a re-report of a closed finding. Verified directly: get_address_masked on the same serializer correctly masks contact info — the name field looks like an oversight, not a deliberate choice.

backend/apps/communications/serializers.py:195-196 backend/apps/communications/views.py:218,227-232
RecommendationRoute get_patient_name through apply_masking/is_masked_role like every other patient-PII serializer, and add a regression test in the existing test_fix_* convention.
Medium

XLSX formula injection in exported reports

Service/medicine name strings are written into openpyxl cells with no sanitization of a leading =, +, -, or @. A name starting with one of these characters (creatable by RECEPTIONIST and other roles with reference-list edit rights) becomes a live formula that Excel evaluates on open — a classic exfiltration vector against whoever opens the report, typically ADMIN/finance staff.

backend/apps/reportes/services/excel.py:51-56
RecommendationPrefix any cell value beginning with =/+/-/@ with a neutral character before writing, applied everywhere free text lands in a generated workbook.
Low

WhatsApp verify token stored in plaintext

whatsapp_verify_token is a plain CharField, unlike its siblings whatsapp_access_token/whatsapp_app_secret on the same model — which a code comment explicitly says are "encrypted at rest like other server-side secrets." The verify token alone can't send messages or read data, so impact is limited, but the handling is inconsistent with the model's own stated intent.

backend/apps/communications/models.py:22-24
RecommendationSwitch to EncryptedCharField for consistency, or document why it's deliberately excluded.

03

Database

No critical issues. The most significant finding is a query pattern that can't use an index and runs twice per report. N+1 queries, foreign-key indexing, and encrypted-field search discipline were all checked across every app and came back clean.

Medium

Non-sargable date filter forces a full scan on every report run

Filtering __year=/__month= on a Coalesce() of two datetime columns can't use any index on either underlying column — Postgres evaluates the expression per row. Confirmed directly: the query also runs twice per request (once for a row-count guard, once for the real aggregate), doubling the cost.

backend/apps/reportes/services/engine.py:52-59
RecommendationReplace the year/month extraction with a half-open date range filter (__gte/__lt) so a plain or expression index becomes usable; add a composite index sized to this query's actual filter shape (status, center, date).
Medium

A migration breaks the project's own schema/index-separation convention

This migration combines an AlterField on an encrypted column with two UniqueConstraints (each backed by an index) in the same transaction — the one place in the patients history where the documented split (schema / backfill / index as separate migrations) wasn't followed.

backend/apps/patients/migrations/0012_alter_patient_cedula_and_more.py:16-28
RecommendationNo action needed if already applied cleanly in production — flagged as a template hazard so it isn't copied as precedent for the next encrypted-field change.
Medium

Same distinct()-plus-default-ordering pattern already fixed once elsewhere

The default model ordering is never cleared before .distinct() — the exact shape a comment elsewhere in the codebase documents as a known past bug (Postgres must append ORDER BY columns to the SELECT list for DISTINCT compatibility, which can silently defeat deduplication). It happens not to break results here only because the ordering column is functionally dependent on id — incidental safety, not structural.

backend/apps/core/services/search.py:57-60
RecommendationAdd an explicit .order_by() before .distinct(), mirroring the fix already applied in reportes/services/engine.py.
Low

No resource limits or tuning on the database container

Neither compose file sets memory/CPU limits or a tuned postgresql.conf for the db service — it runs on stock image defaults on what the project's own docs describe as a single laptop-class host. Connection-count risk is low today (pooling and worker count are both sane), but nothing stops Postgres or a sibling container from starving host resources under load.

infra/docker-compose.yml:6-20 infra/docker-compose.prod.yml:8-9
RecommendationAdd resource limits to the prod overlay and set at least shared_buffers/max_connections/work_mem explicitly.
Low

Backups remain manual and unscheduled

Already known and documented by the project itself, restated here because it's squarely a database-relevant gap for a PHI workload: no cron/Task Scheduler entry exists anywhere in infra/, so backup cadence depends entirely on someone remembering to run the script.

infra/docs/backups.md:15-17
RecommendationWire the existing backup script into Task Scheduler (or a small polling container, matching the pattern already used for Comunicaciones) before real patient data lands.
Info

Report engine's indexes don't cover its real filter combination

Existing indexes optimize for the admission-flow access pattern (patient, status, created_at) — none touches center, which the reporting engine filters by alongside status and a date range.

backend/apps/encounters/models.py:88-92
RecommendationOnce the date-filter fix above lands, add a composite index sized to the report engine's actual access pattern.
4 areas checked and found clean
  • N+1 queries — every views.py checked declares correct select_related/prefetch_related, including nested FK chains and reverse relations feeding computed fields.
  • Foreign-key index coverage — Django auto-indexes every FK; existing composite indexes all match a real filter path in a corresponding view.
  • Encrypted-field search discipline — no queryset filters or orders directly on an encrypted column anywhere; all search paths correctly go through the plaintext search/hash helper columns, applied consistently to newer models too.
  • Migration churn (23 in patients, 15 in records) reflects genuine feature history, not aimless thrash — not flagged as squash-worthy.
