Deploying MedicalConsultations on a Private Network

A complete, beginner-friendly walkthrough for putting this application on a server inside a private network — reachable by computers and phones on that network, but never the public internet. Windows is the primary path; Linux equivalents follow wherever a step differs.

What "private network" means here: the server and everyone using the app are on the same local network (office Wi-Fi, building switch, or a VPN behaving like one). Nothing here opens the app to the wider internet, and no step involves port-forwarding on your router. Internet-facing access needs additional work (a domain name, a real TLS certificate, a reviewed firewall/reverse-proxy setup) that is out of scope for this guide.

1. What you're deploying

The application is three things working together, run by Docker so you don't have to install Python, Node.js, or a database by hand:

PieceWhat it is
dbStores all data (patients, records, appointments).
cacheSpeeds things up internally.
backendThe API — the "brain" of the app.
frontendThe website your staff sees, served over HTTPS with a lock icon (self-signed certificate — see Step 7).
communications_workerSends staff email notices and patient WhatsApp appointment reminders in the background (the "Comunicaciones" module — see section 16 for production setup).

All five run inside containers managed together by Docker Compose, using one command from a folder called infra/. Once running, anyone on the same private network opens a browser to https://<server's-address>. The database and cache are never reachable from outside the containers — only the website is exposed, and only on the local network.

2. Before you start

You will need:

  • A server machine that stays powered on (desktop, repurposed PC, or dedicated server) — Windows 10/11/Server, or Linux (this guide uses Ubuntu/Debian commands; other distros are similar but package managers differ).
  • Administrator access (Windows: admin account; Linux: a sudo-capable user).
  • The three project folders — backend, frontend, infra — copyable onto the server.
  • About 30–60 minutes and ~4 GB free disk space.

Words you'll see repeatedly

  • Terminal / Command line — a text window for typing commands. Windows: PowerShell (Start menu → search, right-click → "Run as Administrator" when a step needs it). Linux: your distro's Terminal app.
  • IP address — the "phone number" of a computer on the network, e.g. 192.168.1.42. Looked up in Step 4.
  • Container — a lightweight isolated box running one piece of the app; Docker starts/stops/rebuilds these for you.

Every command is meant to be copied and pasted exactly, except placeholders in <angle brackets> — replace the whole placeholder with your own value.

3. Step 1 — Install Docker

Windows
  1. Download Docker Desktop for Windows from docker.com (or have it installed for you).
  2. Run the installer; keep the default WSL 2 backend option checked.
  3. Restart if prompted.
  4. Open Docker Desktop once — it must run in the background (whale icon in the system tray).
  5. Confirm in PowerShell: 
    docker --version
docker compose version
    Both should print a version number.
Linux
  1. Install via the official script: 
    curl -fsSL https://get.docker.com | sh
  2. Add your user to the docker group (log out/in to take effect): 
    sudo usermod -aG docker $USER
  3. Ensure the Compose plugin is present: 
    sudo apt-get update && sudo apt-get install -y docker-compose-plugin
  4. Confirm: 
    docker --version
docker compose version

Commands always use docker compose (two words) — the modern plugin — never the older standalone docker-compose. Install the plugin above if you only have the old tool.

4. Step 2 — Get the code onto the server

The three folders must sit next to each other in the same parent folder:

MedicalConsultations/
├── backend/
├── frontend/
└── infra/        <- you will run all commands from inside here

With Git set up:

git clone <backend-repo-url> backend
git clone <frontend-repo-url> frontend
git clone <infra-repo-url> infra

Without Git: copy the three folders (USB drive, network share, however received) into one parent folder, keeping the exact names and sibling layout above.

Then move into infra — every later command runs from there:

cd path/to/MedicalConsultations/infra

5. Step 3 — Configure the environment file

The app reads passwords/settings from .env inside infra/. Never shared or committed to Git — create your own copy per server.

  1. Copy the template — Windows: copy .env.example .env · Linux: cp .env.example .env
  2. Open .env in a text editor and fill in these values (everything else can stay default):
VariableWhat it's forHow to set it
DJANGO_SECRET_KEYBackend cryptographic key. Secret.Command below
POSTGRES_PASSWORDDatabase password. Secret.Command below
REDIS_PASSWORDCache password, required in this setup. Secret.Command below
PII_FIELD_KEYEncrypts patient data at rest. Secret — see warning below.Command below
DJANGO_ALLOWED_HOSTSAddresses the backend accepts requests for.Server IP — Step 4
DJANGO_CORS_ALLOWED_ORIGINSOrigins allowed to call the API.https://<server's-address> — Step 4
TZTimezone for dates/timestamps.e.g. America/Santo_Domingo

Generating the three secrets. If Python is on the server:

# DJANGO_SECRET_KEY
python -c "import secrets; print(secrets.token_urlsafe(64))"

# PII_FIELD_KEY
python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"

If Python isn't installed on the server, use a throwaway container instead (works identically on Windows/Linux):

docker run --rm python:3.13-alpine python -c "import secrets; print(secrets.token_urlsafe(64))"
docker run --rm python:3.13-alpine sh -c "pip install -q cryptography && python -c \"from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())\""

For POSTGRES_PASSWORD/REDIS_PASSWORD, reuse one of the secrets.token_urlsafe(64) outputs, or a password manager's generator.

DJANGO_SECRET_KEY=the-long-random-string-you-generated
POSTGRES_PASSWORD=another-long-random-string
REDIS_PASSWORD=yet-another-long-random-string
PII_FIELD_KEY=the-fernet-key-you-generated

Critical — read before continuing. Once real patient data exists, PII_FIELD_KEY must never be changed. Changing it makes every existing patient record permanently unreadable, with no recovery. Set it once correctly before going live, and keep a secure backup of .env (see Backups). If rotation is genuinely needed later, that requires the dedicated reencrypt_pii command — see Troubleshooting.

Never commit .env to Git, email it, or store it anywhere but the server and a secure backup.

6. Step 4 — Find the server's network address

Windows 
ipconfig

Look for IPv4 Address under your active adapter, e.g. 192.168.1.42.

Linux 
hostname -I
# or
ip addr

Look for an address starting with 192.168., 10., or 172.16.–172.31. — private-network ranges.

Fill in .env using that address:

DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,backend,192.168.1.42
DJANGO_CORS_ALLOWED_ORIGINS=https://192.168.1.42

An IP can change after a reboot or router restart. If it does, the app rejects requests for the new address until .env is updated and backend restarted (Day-to-day operation). Ask your network admin about reserving a static/DHCP-lease address for the server.

7. Step 5 — Start the application

From infra/:

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build

This one command: builds everything (first run: several minutes), generates a self-signed HTTPS certificate, sets up the database, and starts all five containers in the background.

Watch it come up:

docker compose -f docker-compose.yml -f docker-compose.prod.yml ps

Expect five containers — mc_prod_db, mc_prod_cache, mc_prod_backend, mc_prod_frontend, mc_prod_communications_worker — as running/healthy. If not, check logs:

docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f
docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f backend

Ctrl+C stops watching logs without stopping the app.

If mc_prod_frontend fails the very first time with a missing-certificate error, that's a brief startup race between nginx and the certificate generator. Just re-run the up -d command — safe to run repeatedly.

8. Step 6 — Create the admin account

docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backend python manage.py create_admin --username admin --email admin@example.com --password "ChangeMe123!"

Replace admin, the email, and especially the password with your own values — don't leave the example password in place. You'll use these to log in next.

9. Step 7 — Open it from other computers on the network

Allow the connection through the firewall

Open ports 443 (HTTPS) and 80 (redirects to 443).

Windows (PowerShell as Administrator) 
New-NetFirewallRule -DisplayName "MedicalConsultations HTTPS" `
  -Direction Inbound -LocalPort 443 -Protocol TCP -Action Allow -Profile Private
New-NetFirewallRule -DisplayName "MedicalConsultations HTTP Redirect" `
  -Direction Inbound -LocalPort 80 -Protocol TCP -Action Allow -Profile Private
Linux (ufw) 
sudo ufw allow 443/tcp
sudo ufw allow 80/tcp

(firewalld instead: sudo firewall-cmd --permanent --add-port=443/tcp --add-port=80/tcp && sudo firewall-cmd --reload.)

Never forward these ports on your router. The rules above only open ports on your local network (-Profile Private keeps Windows off Public/Domain networks too). Port-forwarding on the router exposes the app to the entire internet — this deployment is reviewed for private-network use only.

Browse to the app

From another device on the same network:

https://192.168.1.42

(Replace with your server's actual address from Step 4.)

About the "not secure" / certificate warning

Expected — the app uses a self-signed certificate rather than one from a public certificate authority (which needs a public domain name). The connection is still encrypted; the warning only means the browser doesn't recognize the issuer. Safe to proceed on a trusted private network:

  • Chrome/Edge: "Advanced" → "Proceed to <address> (unsafe)."
  • Firefox: "Advanced" → "Accept the Risk and Continue."

Each device shows this once (or after the certificate regenerates). A real certificate for an internal domain can later be mounted in its place — beyond this guide's scope.

10. Step 8 — Verify everything works

  1. Log in at https://<server-address> with the admin credentials from Step 6.
  2. Confirm the health check (from any machine on the network): 
    curl -k https://192.168.1.42/api/health/
    (-k ignores the self-signed certificate warning, same as clicking through it in a browser.)
  3. Have another device open the same address and confirm it loads and logs in too.

If all of that works, the deployment is complete and ready for regular use.

11. Day-to-day operation

Run from infra/. Every command below targets the production stack (both -f flags needed).

# Stop the app (data preserved)
docker compose -f docker-compose.yml -f docker-compose.prod.yml down

# Start it again
docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d

# Check status
docker compose -f docker-compose.yml -f docker-compose.prod.yml ps

# View logs
docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f [service-name]

After receiving updated code, rebuild and restart:

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --build

New database migrations run automatically whenever backend restarts — but only on restart. The --build + up -d command above always restarts it, so prefer that over trying to skip steps.

Day-to-day settings (login lockout, session lifetimes, rate limits, upload size, page size) usually don't need Docker at all — an administrator can change these live from the app's own Settings page. Reserve redeploys for actual code updates.

Destructive, avoid unless you mean it: down -v permanently deletes the database and all uploaded files. Never run this on a server with real data without a current backup.

12. Backups

Data lives in two places that must be backed up together: the database and the uploaded-media folder.

Running a backup

./scripts/backup_db.ps1

Creates two timestamped files in infra/backups/: pgdata_<timestamp>.dump (database) and media_<timestamp>.tar.gz (uploaded files). Keeps 14 days by default (-RetentionDays 30 to change) and can target a different folder (-BackupDir "D:\Backups").

Restoring a backup

./scripts/restore_db.ps1 -DumpFile "infra/backups/pgdata_2026-08-21T140005.dump" `
  -MediaArchive "infra/backups/media_2026-08-21T140005.tar.gz" -Confirm

-Confirm is required on purpose — restoring replaces all current data. Afterward:

  1. Apply pending migrations: 
    docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backend python manage.py migrate
  2. If PII_FIELD_KEY changed since that backup, run the re-encryption command with the old key first — see Troubleshooting.

Running backups on Linux

These scripts are PowerShell, which also runs on Linux via PowerShell Core (pwsh) — no separate Bash version exists.

sudo apt-get update && sudo apt-get install -y wget apt-transport-https software-properties-common
wget -q "https://packages.microsoft.com/config/ubuntu/$(lsb_release -rs)/packages-microsoft-prod.deb"
sudo dpkg -i packages-microsoft-prod.deb
sudo apt-get update && sudo apt-get install -y powershell
pwsh ./scripts/backup_db.ps1
pwsh ./scripts/restore_db.ps1 -DumpFile "infra/backups/pgdata_....dump" -Confirm

Scheduling backups automatically

Nothing schedules backups by default — set up a recurring job:

Windows — Task Scheduler
  1. Task Scheduler → Create Basic Task, name it, choose a daily trigger.
  2. Action: Start a program → pwsh.exe (or powershell.exe) → Arguments: -File "C:\path\to\infra\scripts\backup_db.ps1".
  3. Finish, then right-click → Run once to confirm it works.
Linux — cron 
crontab -e
0 2 * * * pwsh /path/to/infra/scripts/backup_db.ps1 >> /var/log/mc-backup.log 2>&1

Copying backups off the server

The scripts only write to a local folder — if that disk fails, backups fail with it. Periodically copy infra/backups/ to a second drive, network share, or off-site storage; there's no built-in automation for this, treat it as a manual habit. Backup files carry the same patient data as the live database — handle with the same care.

13. Troubleshooting

A port is already in use / the app won't start.
Windows: Get-NetTCPConnection -LocalPort 443 · Linux: sudo ss -tulpn | grep :443. Stop whatever else is using it, or change the service's bound port (see docker-management.md).

A container keeps restarting or shows "unhealthy."

docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f <service-name>

Read the last log lines. Common first-boot cause: frontend starting a moment before its certificate is ready — see the tip at the end of Step 5.

Browser shows a certificate warning. Expected — see Step 7, not a sign of a problem.

Forgot the admin password. Create a new admin with a different username (Step 6), or ask your developer about resetting a password via Django's admin tools.

Accidentally changed PII_FIELD_KEY and can't read patient data. Don't panic or restart repeatedly — put the old key back in .env immediately, then have your developer run the rotation command properly if a change is truly needed:

docker compose -f docker-compose.yml -f docker-compose.prod.yml exec backend python manage.py reencrypt_pii --old-key <OLD_KEY>

This safely re-encrypts every record instead of leaving old data unreadable. Only do this with guidance if unsure — it touches every patient record.

The server's IP changed and nothing loads. Update DJANGO_ALLOWED_HOSTS/DJANGO_CORS_ALLOWED_ORIGINS (Step 4), then:

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --force-recreate backend frontend

14. Security notes

  • Database and cache publish no ports at all — reachable only by the other containers, never directly from the network. Already configured correctly; don't add port mappings for them.
  • The self-signed certificate is appropriate only because this deployment is private-network-only. Don't reuse it for anything reachable from the public internet.
  • Keep .env readable only by administrators — it holds every password and encryption key the app depends on.
  • Never set DJANGO_DEBUG=true on a real deployment. The production compose file forces it to false, and the app refuses to start in production with a missing or default-looking secret key, database password, or PII_FIELD_KEY. Fix the actual value instead of working around the failure.
  • Every meaningful action (creating, editing, viewing sensitive records) is written to an audit log automatically — nothing extra to configure.

16. Configuring Comunicaciones for production (staff email & patient WhatsApp)

Comunicaciones is the module that sends staff notices by email and appointment reminders to patients over WhatsApp. It runs on a fifth background container, communications_worker (mc_prod_communications_worker in this stack) — already started automatically by the same up -d --build command from Step 5; there is no separate service to install. It polls every 60 seconds and has nothing to configure on its own — the two channels below are configured separately.

Staff email

Comunicaciones reuses the clinic's own mailbox — it never sets up a second email service. Add these to .env (they're optional; leave EMAIL_HOST blank and staff-email sending simply stays off until it's filled in):

VariableWhat it's for
EMAIL_HOSTYour mail provider's SMTP server, e.g. smtp.gmail.com or smtp.office365.com.
EMAIL_PORTUsually 587 (STARTTLS).
EMAIL_HOST_USERThe mailbox's login/address.
EMAIL_HOST_PASSWORDIts password — for Gmail/Google Workspace this must be an App Password, not the regular account password. Secret.
EMAIL_USE_TLSLeave true.
DEFAULT_FROM_EMAILThe "From" address staff see, e.g. no-reply@yourclinic.com.

After editing .env, restart the backend and worker so they pick up the new values:

docker compose -f docker-compose.yml -f docker-compose.prod.yml up -d --force-recreate backend communications_worker

Test it once logged in as an Admin: Comunicaciones → Ajustes → Correo → "Enviar correo de prueba."

Patient WhatsApp

Unlike email, WhatsApp is not configured through .env at all — an Admin enters it directly in the app, under Comunicaciones → Ajustes → WhatsApp, after logging in. Nothing sends until this is done; the master switch stays off by default.

  1. Provision WhatsApp Business Cloud API access with Meta first — that process (business verification, app creation) is Meta's own and outside this guide. You'll come out of it with four things: a phone number ID, a business account ID, a permanent access token, and an app secret.
  2. Log in as Admin → Comunicaciones → Ajustes → WhatsApp → paste those four values, confirm the default country code (prefilled +1 for the Dominican Republic), set the reminder lead time (default 24 hours before the appointment), then turn on "Activar WhatsApp a pacientes."
  3. Templates. WhatsApp only ever sends Meta-pre-approved template messages — never free text. Before any patient WhatsApp will actually go out, create/activate one template row per kind under Comunicaciones → Plantillas (cita_creada, cita_recordatorio, cita_reagendada, cita_cancelada), matching the exact template name and language Meta approved for your account. A missing or inactive template for a kind fails just that one send with a clear in-app message ("Falta plantilla de WhatsApp para {tipo}") instead of breaking anything else.
  4. Test it with "Enviar WhatsApp de prueba" on the same Ajustes page (stays disabled until the token and phone number ID are both saved).

The webhook needs the public internet — this guide's private-network setup does not provide that. Meta's servers deliver delivery-status updates (Sent → Delivered → Read) and inbound replies — including a patient texting STOP/SALIR/NO/CANCELAR to opt out — by calling a webhook URL on your server, which means Meta must be able to reach your server over the internet. This deployment, as described in this guide, is reachable only from your local network (see the note at the top of this document), so the webhook cannot be wired up as-is.

What still works without it: sending itself only needs outbound connectivity (your server calling out to graph.facebook.com), so appointment reminders and notices still send normally.

What doesn't: delivery status will sit at "Sent" and never advance to "Delivered"/"Read" in the Comunicaciones log, and a patient replying STOP will not be opted out automatically — a staff member has to turn off "Notificaciones por WhatsApp" on that patient's record by hand instead if the patient asks to stop receiving messages.

If your organization later decides to expose this deployment to the public internet (a real domain name, a real TLS certificate, a reviewed reverse-proxy/firewall setup — all outside this guide's scope; get a developer or ops professional involved for that), only then register the webhook: copy the read-only Webhook URL shown on the Ajustes → WhatsApp page, set a Verify Token on that same page, and enter both in the Meta App dashboard under WhatsApp → Configuration → Webhook, subscribed to the messages field.

If messages seem stuck

Queued email/WhatsApp messages send within about a minute (the worker's poll interval). If something sits in "Queued" longer than that, check the worker's own logs:

docker compose -f docker-compose.yml -f docker-compose.prod.yml logs -f communications_worker
See also, in this same folder: docker-management.md for deeper compose-file mechanics and backups.md for the full backup/restore design notes.
